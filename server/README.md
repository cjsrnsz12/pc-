# Shared rooms, protocol 1

The Android and Windows clients opt in by creating or joining an invitation-code room. They send nickname, platform, version, execution state, content, current-run UUID, completed count and a persisted increasing sequence. No screenshot, game account, game command or log is transmitted. Joining a room does not permit remote control.

Deploy `schema.sql` through a Supabase migration, then deploy `index.ts` as `nyacro-rooms` with gateway JWT verification disabled. The handler authenticates each membership using a random 256-bit client token, with only a SHA-256 hash stored in the database. The service-role credential stays in the Edge Function environment. The two app configurations contain only the public endpoint and publishable key. The private schema has RLS enabled and no client grants or policies (intentional default deny). Only service_role can execute the invoker RPC. Private table RLS-without-policy informational advisories are expected.

Rooms use random 80-bit codes. Members can see only their own room. Poll every 15 seconds; presence becomes offline after 60 seconds. Stopped clients retain their last completed count; a new run UUID permits resetting it. Stale sequences cannot overwrite newer updates, and the count cannot decrease within a run. Entries are hidden after 24 hours without a heartbeat and removed after 7 days when a new room is created. Empty rooms older than a day are cleaned up on creation. Each room admits 50 recent members; room count and operation rates are bounded. Rate keys are an HMAC of the gateway-provided IP; raw IPs are not stored. Membership credentials are stored only in private local app settings and omitted from UI, logs, exports and server responses.

Create/join retries reuse the same credentials to avoid duplicates after response loss. Leaving clears locally only after saving succeeds, then revokes the remote membership. Network loss cannot block capture or gestures, and a stale response cannot restore a left room. A process restart reports stopped rather than reviving a previous running state.

`verify.sql` performs transactional contract/security assertions and rolls back all test records. Python `test_room_sync.py` covers opt-in, retry, persistence, sequence, disconnect and in-flight leave. Android `tests/run_room_tests.py` compiles the actual Java RoomApi/RoomSync with minimal Android preferences/clock adapters and exercises the deployed service alongside the actual Python API. It does not run Android UI or the game. Native Windows CI exercises the room UI with an offline fixture and builds/tests the executable before release.
