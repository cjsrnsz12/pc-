# Global player directory (protocol 2)

New Android and Windows releases require an initial nickname submission. The form explicitly says that nickname, mobile/PC, execution state, content and current-run completed count become visible to all Nyacro users. Once saved, the profile reconnects automatically. No room creation or invitation code is involved. Neither client reads or migrates the old private room settings. The legacy protocol1 and its schema/RPC remain for older clients.

`players.sql` creates a new private, RLS-enabled schema and an invoker RPC callable only by service_role. Apply it as a reviewed migration. The Edge Function dispatches players_register/players_sync/players_remove to this contract and preserves old room operations. Public apps contain only the endpoint and publishable key. A cryptographically random membership token authenticates each device; only its hash is stored on the server. Consent_version2 is mandatory for registration. Nickname changes authenticate the same identity. Names can repeat; device and self markers distinguish rows.

Presence polling runs on one coalescing worker every15seconds, independent of game capture and gestures. The list contains profiles with present=true and a heartbeat within60seconds,100rows per page with a total. Closed PCs send present=false; disconnected clients expire after60seconds. A new run UUID resets the count; a stopped run retains it. Persisted increasing sequences reject stale updates and same-run counts cannot decrease. Requests and response sizes, rates and retained profile count are bounded. Cleanup removes inactive7day profiles during registration. HMAC rate keys do not retain raw IP addresses. The API returns no membership tokens, hashes, IPs or private room records.

Tests: `test_players_sync.py` covers required onboarding, no private migration, explicit consent, offline retry, rename, stale responses, count/state, persistence and save failure. `players_smoke.py` exercises actual native Windows form controls, both platform rows, rename and pagination without networking. Android `tests/run_player_tests.py` compiles actual PlayerApi/PlayerSync with minimal preferences/clock adapters; `--live` additionally exercises the deployed server with actual Java mobile and Python PC clients. Actual Android UI and game operation are not covered.

## Cumulative totals

Apply `lifetime.sql` to existing deployments; fresh installations use the updated `players.sql`. Existing retained current counts initialize the lifetime total. Older reset history cannot be reconstructed. Keep `completed` for old clients and current-run state. New lists render the64bit `lifetime_completed`, and the response includes self_lifetime_completed even when the requester is on another page. New clients persist cumulative totals, add only positive completion deltas, and never clear them at a new run. They reconcile server totals while preserving completions made during an in-flight request. Client-supplied lifetime values are merged with max (not added again), so registration/retry and offline recovery cannot double count a run. Legacy requests without a lifetime value add only server-observed run deltas, guarded by the persisted increasing sequence. The local retained lifetime rehydrates a profile after server cleanup. Names, credentials and privacy settings are unchanged.
